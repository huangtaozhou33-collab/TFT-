# 工程踩坑与解决记录

本文用来说明“出现了什么问题、为什么、怎么解决、怎样证明有效”。记录日期从 2026-10-10 开始；前期事项按现有验收记录补录，不把补录日期当作故障发生时间。

每次实质性修复都在这里追加或更新对应条目。验证通过只适用于记录中的代码、数据和配置，不自动覆盖后续修改。原始验收摘要见 [RAG_VALIDATION.md](RAG_VALIDATION.md)。

## 1. Docker Desktop 启动失败：残留的 Secrets Engine socket

**现象**：Docker Desktop 报错，无法将 `docker-secrets-engine/engine.sock` 改名为 `engine.sock.stale`，数据库容器无法启动。

**原因与证据**：错误发生在 Docker Desktop 的本机 Secrets Engine 初始化阶段，而不是 MySQL、Redis 或 Milvus 的业务连接阶段。停止失败的 Docker 进程、保留并移开该目录后可以重新启动；现有证据不足以断定最初是哪一个进程造成文件占用或异常状态。

**处理**：核实 Docker 相关进程及路径，停止失败进程；把本机 `docker-secrets-engine` 目录改为带时间标记的保留目录，再启动 Docker Desktop。没有清空镜像、数据库卷或执行恢复出厂设置。

**验证**：Docker Engine 恢复响应，项目的 app、MySQL、Redis、Milvus、etcd、MinIO 六个服务均达到 healthy。

**经验与限制**：先定位失败层级，再采用可恢复的最小改动。不要把 Docker Desktop 本机 socket 异常当作数据库坏掉，更不要先删数据卷。本次修复有效，但没有证明未来所有同类报错均可这样解决。

## 2. 启用严格版本过滤后，推荐阵容和单英雄出装全部为空

**现象**：首页和筛选器显示“来源统计补丁未知或与当前补丁不同，不能用于当前版本查询”，用户原来能查看的结果消失。

**根因**：切换到 MySQL 后，统计输出增加了“来源补丁必须已知且等于运行补丁”的限制。初始包的 204 份统计快照中，有 202 份 OP.GG 快照未提供可核验的来源补丁；已采集数据仍在库中，但都被过滤。该数量是统计快照数，不能误写成英雄数、文档数或对局样本数。

**处理及状态（2026-10-10 更新）**：先拆开“补丁未知”和“补丁不匹配”提示，但这一步本身没有恢复数据。本轮按用户授权增加有依据的推定归档，201 份实际统计恢复可用；原始来源版本仍保留为空，页面标注“18.4 · 推定”。另 1 份本就不支持的统计不伪造结果，见第 8 条。

**验证**：前期基础设施检查证明未知补丁统计会被隔离、原始快照仍保留。相关接口能返回 HTTP 200 及 unavailable 状态；HTTP 200 只能证明接口处理成功，不能证明页面有可用结果。

**经验与限制**：严格版本隔离具有价值，但在未补齐数据源版本信息前直接上线，会使已有功能失效。发布前应同时检查数据覆盖和关键用户路径，不能只检查过滤规则是否正确。来源“未提供补丁”也不等于“已经证实过期”。

## 3. 数据交付方式白名单没有随 MySQL 接入更新

**现象**：数据已经通过 MySQL 获取，但下游仍把它当成不支持的来源，提前拒绝展示或处理。

**根因**：部分检查只接受原有的 `delivery: version_cache`；数据库接入后返回 `delivery: mysql`，下游未同步适配。这里的 delivery 表示数据怎样交付，并不等同于数据来自哪家网站，也不能替代补丁验证。

**处理**：让相应交付检查接受 MySQL 路径，同时保留统计补丁和联合样本等独立校验。

**验证**：该次修复后的历史记录为 263 项测试通过，并完成数据库集成检查。后续整体回归达到 269 项通过，见验收记录。未知补丁数据仍被限制，因此不能把这个兼容修复当成全部空白问题已解决。

**经验**：替换存储后，要沿接口返回值追踪下游状态判断，尤其是来源枚举和白名单。数据存储方式、统计来源、补丁资格应分别判断。

## 4. 填好 Embedding 配置后，仅刷新网页不会让容器读取新配置

**现象**：用户已在本地填写模型配置，但运行中的应用不会仅因浏览器刷新而获得这些配置。

**根因**：容器的环境变量在创建时注入；修改宿主机配置文件不等于修改了现有应用进程的环境。普通重启也不应被当作已重读 Compose 配置的保证。

**处理**：重新创建应用容器，使其加载配置；先用两条中英文短文本验证接口，再构建知识索引。密钥仅保留在本地配置中，文档与验收输出不记录密钥。

**验证**：`qwen3.7-text-embedding` 的真实接口调用成功；678 个合格片段分别生成 1024 维向量，完成 Milvus 写入数量与逐 ID 回查，应用容器重新创建后索引仍可用。678 是该次种子发布的合格片段数，1024 是每条向量的维度，两者不能混为文档数量。

**经验与限制**：分别验证“配置已加载”“接口能调用”“索引已写入”“查询实际使用索引”。文本与向量可以重建，MySQL 原文和发布元数据是追溯依据。更换模型或输出维度应重建并重新验收索引，不能混用不同模型的向量。

## 5. 向量最近邻会给无关问题返回看似相关的云顶资料

**现象**：首轮真实检索中，烹饪问题也返回了云顶知识片段。

**根因**：最近邻搜索会在库里选出“相对最近”的文本，即使全部候选都不相关。只取 top-k 而缺少最低相关度判断，不能回答“是否应该检索到内容”。微弱关键词重叠也不应让低分向量重新成为有效证据。

**处理**：给当前 COSINE 检索增加 0.5 的初始相关度下限；明确实体、完整别名和完整标题匹配保留。无关问题不再通过词法降级重新引入噪声；阈值纳入缓存隔离，避免改配置后继续命中旧结果。

**依据**：本次小样本中，3 条无关问题的最高分约为 0.30～0.37；知识与别名正例约为 0.73～0.89；两条额外口语问题约为 0.57～0.64。**0.5 不是事实置信度，也不是所有模型通用阈值**，只是在当前模型与语料上的初始选择。

**验证**：真实检索验收 10/10 通过，包括 7 条正例与烹饪、天气、护照 3 条负例；负例均返回空证据。同期 269 项项目测试通过。一次真实聊天问“八级商店四费概率”，返回 30% 并引用来源。结果见 [RAG_LIVE_VALIDATION.json](RAG_LIVE_VALIDATION.json) 和 [RAG_CHAT_VALIDATION.json](RAG_CHAT_VALIDATION.json)。

**经验与限制**：评测同时需要“该找得到”的正例和“不该返回”的负例。10 条检索及一次聊天只是小规模验收，不能保证所有无关问题均被识别。新增语料、更换模型或调整阈值后，应重新评测召回与误召回；统计问题仍走结构化数据查询，不能用相似度补造胜率。

## 6. 基础设施检查可能意外调用已配置的收费模型

**现象**：应用接入真实 Embedding 后，原本只用于检查存储的脚本也可能经过正常检索路径调用模型提供商，导致普通验证产生外部调用和费用。

**根因**：检查复用了应用运行配置与知识检索入口；“只是跑基础设施检查”并不自动保证它不会触发模型。此处记录的是已发现并修复的调用风险，不声称核实了实际账单金额。

**处理**：`check:storage` 为自身检查显式使用禁用模型的配置；真实提供商测试单独通过 `check-rag-live.mjs --allow-provider` 执行。检查配置不覆盖正式应用的混合检索配置。

**验证**：容器内基础设施检查通过 MySQL、Redis 和临时 Milvus 集合验证，结果标记 `embeddingProviderCalled: false`。真实模型验收另行显式执行并记录。

**经验**：自动化测试的边界必须由配置和代码保证，不能只靠命令名称。涉及费用、外部服务和真实数据的验证应与日常回归分开。

## 7. 开发者页显示 5000 多个文档，却只有 1900 多个可检索：混用了计数单位

**现象**：用户看到开发者页两组明显不同的数量，希望明确哪些资料被排除以及原因。

**根因与证据**：旧界面把 JSON 来源包按实体、规则生成的展示记录写成“文档”，又把目录中已映射工具的记录数写成可检索数量，容易被理解为 Milvus 文档数。实际 5348 条由以下互斥组组成，合计完全相等：

| 来源记录分类 | 数量 |
| --- | ---: |
| 当前来源记录，已映射工具 | 1935 |
| 留存的历史修订 | 3312 |
| 阵容码编号映射 | 75 |
| 未匹配实体的专家评级 | 13 |
| 参考版本或冲突规则 | 7 |
| 身份未核实的法杖条件 | 6 |

当前 MySQL 发布有 **641 份知识文档，596 份满足检索资格；切分后共 749 个片段，678 个满足资格并已写入 Milvus**。不合格的 45 份文档为：资料库参考 5、冲突 2、强化规则待核验 2、法杖条件冲突 28、法杖条件待核验 8。片段不是文档，一份文档可切成多个片段。1935 也不表示 1935 条向量。

**处理**：开发者页以当前数据库实际文档、片段及索引状态为主；来源归档单独展示上述分类和单位。另外发现 Docker 镜像按配置不包含本地 OP.GG 原始缓存文件，旧扫描器将“镜像没有文件”误判为 204 份数据校验失败。现改为“本地文件未随镜像交付”，数据库状态独立核验；真正的文件哈希不匹配仍报错。

**验证**：实际 SQL、存储接口与开发者接口返回上述计数，刷新后的开发者页面也显示 641 / 596 / 749 / 678，并单列 5348 条来源记录及其分类，见 [STATISTICS_ATTRIBUTION_VALIDATION.json](STATISTICS_ATTRIBUTION_VALIDATION.json)。最终 285 项测试通过，来源分类计数、历史修订和 Docker 缺文件分支已覆盖。678 条向量未删除或重新生成。

**经验**：展示数量时应同时标明单位、发布或补丁范围、统计时间和资格条件。计数差异只有在分母一致后才有解释意义。

## 8. OP.GG 未携带补丁时，按采集日推定补丁：实现与验收

**现象与用户决定**：首页和单英雄出装被“补丁未知”挡住。当前轮次用户明确允许：OP.GG 缺少版本编号时，依据原始采集当天对应的游戏补丁补充归档并继续返回，同时保留推定的性质。

**根因与证据**：本轮实际发现 6 个 TFT 工具并调用其中 5 类；玩家风格工具需要 PUUID，未调用。阵容响应有统计时间和总数元数据，但没有版本；英雄出装和装备持有者响应也没有版本。装备合成资料表明确返回 18.4，只能证明该资料表自身版本。英雄/装备参数枚举分别为 80 / 142，不能把枚举数当作已收录或非空统计数量。详细字段、能力边界与原始响应位置见 [OPGG_DATA_CONTRACT.md](OPGG_DATA_CONTRACT.md)。

**版本依据**：Riot [官方日历](https://support.riotgames.com/en-us/tft/events/patch-schedule-teamfight-tactics/)列出 18.4 计划于 2026-10-07 PT 上线；本次 [OP.GG 默认阵容页](https://op.gg/zh-cn/tft/meta-trends/comps)也明确选中 18.4。旧快照在 10 月 7 日 UTC 采集，正逢切版日，不能由日历证明全部地区及统计已完成切换。[官方公告](https://teamfighttactics.leagueoflegends.com/en-us/news/game-updates/teamfight-tactics-patch-18-4/)还记载同日 B 更新及平台分批推出，因此仅归档主补丁 18.4，B 更新状态保留未知。资源版本 16.20 不作为统计补丁证据。

**具体改法**：增加 `snapshot_patch_assignments`，用发布 ID、快照键和 `contentHash` 绑定归档；保留原 `sourcePatch:null`，另存 `assignedPatch:18.4`、`manual_calendar` 判定方法、时间窗口、证据链接和切版提示。策略限制原种子发布、赛季与原始采集时间；明确来源版本优先，变更写入 `change_log`。统计归档不改变知识发布，也不重新调用 Embedding。原 202 份缺版本统计中，201 份已归档，另 1 份 `not_supported` 不能靠补版本产生数据。

**自动发现准备**：新增只读 `probe-opgg-patch.mjs`，优先解析 OP.GG 当前选中版本，Riot 日历只作辅助核对；报告包含 `checkedAt`、页面哈希及证据 URL。它不修改数据库、不提升当前补丁、不启动排程。未来选项、脚本中的版本和 URL 参数都不会被当作当前选中版本；歧义返回 unknown。

**已完成验证**：5 类真实 MCP 返回已保存；10 项版本探测器测试通过，真实官网探测返回 `assignedPatch:18.4`、`sourcePatch:null`、`method:source_page`，与日历一致。数据库实际为 2 份来源明确版本、201 份推定版本、1 份不可用。首页接口恢复 10 套阵容；奈德丽返回 591 条出装，最低样本量 100 后剩 54 条，筛选器本次展示前 30 条。第二次执行归档为 `eligible:201, changed:0`，证明重复执行不重复改写。多英雄联合统计仍明确不支持。285 项测试全部通过；容器内 `check:storage` 通过归档、未知补丁和跨补丁隔离等检查，`embeddingProviderCalled:false`。原始采集时间仍为 10 月 7 日，这次没有重新采集整包统计。

**浏览器验收**：重新加载实际 3001 页面后，首页显示“10 / 10 套来源阵容”和“18.4 · 推定”；筛选器显示奈德丽装备图片、前 30 / 54、平均名次、前四率、登顶率及样本数。界面截图见 [筛选器恢复验收](STATISTICS_EXPLORER_RESTORED.jpg)。只刷新前端不会重跑 Embedding 或重新采集上游统计。

**可复用经验与限制**：日期归档是有证据的推定，不能改写成来源自报版本；执行日期不能替代采集日期，日历计划日期也不是精确上线时刻。版本号要取当前控件或明确字段，不能取网页上数字最大的未来版本。统计 API 未提供段位、多英雄同场等条件，补版本只能恢复既有能力，不能创造联合样本；当前只读探测器也不等于自动更新系统已经上线。

## 9. MySQL JSON 小数往返导致哈希不同，首页仍被拦截

**现象**：第一轮归档只成功 200 份，单英雄装备恢复了，但首页仍没有阵容；不能据此认定上游缺失阵容。

**根因与证据**：阵容快照在 MySQL JSON 中经过浮点数解析与序列化，4 个小数的最后几位与校验过的种子不同。例如 `2.0540834195849134` 读回为 `2.054083419584914`。存储的原始哈希与种子一致，但对读回 JSON 再计算哈希不同。SHA-256 是逐字节比较，即使极小的数值往返误差，也会得到完全不同的摘要。

**处理**：保留严格哈希校验作为首选。只有在另有校验通过、哈希与存储值一致的原始种子可作对照时，才逐字段检查往返一致性：键、类型、字符串、整数必须完全相同；有限非整数的差异最多允许 `4 × Number.EPSILON × 数值绝对值`。该路径标记为 `seed_hash_and_mysql_numeric_roundtrip`。没有原始对照、结构变化、整数变化或实质指标变化都不放行；不改写原始数据及哈希。

**验证**：新增回归验证真实小数差异可通过，但 `2.06`、计数从 100 改为 101、版本字符串变化、数组变对象等均不通过。最终归档 201 份，首页 10 套恢复，678 个原有向量继续可用；完整 285 项测试及实际存储检查通过。

**经验与限制**：内容摘要需要定义“原始字节”还是“规范化后的业务内容”。跨数据库存取 JSON 数字时，两者不能默认相同。此次只为已有、可独立校验的种子提供窄范围兼容，未来采集流水线应保存原始响应字节或约定稳定的数值编码，不能把宽松近似比较当作普遍完整性校验。

## 10. 源码已有 Riot Key 字段，但 Docker 没有传入

**现象与根因（2026-10-10）**：准备填写 Riot 开发 Key 时，源码和 `.env.example` 已有 `RIOT_API_KEY`，但 Docker Compose 未向 app 注入它，首次生成 `.env.docker` 的模板也缺少该字段。因此填写开发用 `.env` 不能让 3001 容器获得配置。

**改法**：在 Compose 和新安装模板补上 `RIOT_API_KEY`、`RIOT_REGION`；已有本机 `.env.docker` 仅追加缺少的字段，保留原有配置。当前 Key 填写入口是 `.env.docker`，不通过聊天框或前端表单传递。

**验证与边界**：`docker compose --env-file .env.docker --profile rag config --quiet` 通过；`git check-ignore .env.docker` 确认其被忽略，镜像构建规则也排除环境文件。此次未打印密钥、未重新创建容器、未调用 Riot API。用户填好后需要重新创建 app 才注入新值；配置传递就绪不等于 Riot 采集器已实现。`asia` 是原有区域默认值，具体采样平台及路由在采集阶段核定。

**经验**：配置文件里出现一个 Key 名称，不代表运行中的服务已经能读到它；要沿“填写位置 → 启动配置 → 容器环境 → 服务读取”逐层核对。

## 11. Riot Key 已加载且格式正确，但真实请求仍返回 401

**现象（2026-10-10）**：用户填写开发 Key 后，向官方韩服 `/tft/league/v1/challenger` 发起一次只读验证，HTTP 返回 401。未开始请求比赛，也未切换数据源。

**已核实与未核实**：本机 `.env.docker` 的 Riot 字段非空、符合 RGAPI UUID 外形、无首尾空白，实际进程值与文件相同。应用容器重新创建后同样加载非空且格式正确的值。请求使用 `X-Riot-Token`，只发向固定 Riot HTTPS 域名，禁止重定向。可以排除本轮发现的“没读到配置”问题；不能仅由格式和 401 判断一定是过期、复制错误或账号权限，具体认证拒绝原因尚未确认。

**处理与下一步**：认证失败后停止继续请求，不循环重试、不轮换其他凭证。由用户在 Riot 开发者平台重新生成开发 Key，覆盖本机字段后再验证。格式检查通过只说明值的外形正常，不表示服务端认可该凭证。

**实际验证**：只请求一次认证接口，比赛采集数为 0；应用健康接口 HTTP 200，原阵容接口仍 ready，Milvus 已连接且原有 678 条索引仍在。只保存不含密钥、玩家标识和响应正文的 [验证摘要](RIOT_API_VALIDATION.json)。没有输出密钥，也没有进行未经认证的比赛采集。

**后续结果（同日）**：用户更新 Key 后，相同韩服接口返回 HTTP 200，取得 400 条王者榜记录，随后完成第 12 条的小批采集。配置位置和请求路径没有改变；这证明更新后的凭据有效，但仍不足以断定前一个 Key 的具体失效原因。验证摘要保留前次 401 时间与本次成功结果。

## 12. 官方比赛接口通了，也不能省略字段与模式核验

**现象**：新 Key 成功取得 12 场 S18 比赛，但其 `game_version` 全部为 `TFT Unreal Version ?.?.?.?`。数据包含 7 场普通排位（1100）、4 场普通模式（1090）、1 场其他队列（1220）；按王者玩家取近期战绩，也不会自动只返回排位。

**根因与证据**：本次上游确实返回占位版本字符串；已直接读取原始响应，不能把这是“双人作战特例”当作普通排位字段完整的保证。Match ID 接口没有 queue 参数，必须在比赛详情层检查模式。全部样本 89 条终局，普通排位单独为 56 条，不能把混合模式的玩家数直接当作排位分母。

**处理**：新增小批只读 `probe-riot.mjs`，固定官方 HTTPS 目标、Key 只放请求头、禁止重定向，遇到认证失败或限流停止。每次最多从 3 个王者种子玩家各取 5 个近期比赛 ID，再去重读取最多 12 场；这只是字段验收样本，不声称总体代表性。原始记录保存到 Git 忽略的 `data/raw/riot-probes/`，脱敏报告另存；没有写入业务数据库，也没有给 Riot 数据自动赋予 18.4。

**实际结果**：本轮 1 次榜单、3 次比赛列表、12 次比赛详情，共 16 次请求全部 HTTP 200。7 场普通排位全是 8 人且名次完整，共 455 个棋子记录，英雄 ID 全部精确映射；660 次 `itemNames` 出现中 658 次映射，`DA_BlastPotion18` 和 `DA_HealthPotion18_Radiant` 各 1 次未映射。实际没有数字 `items` 字段，不能依赖文档中另一个字段或猜数组位置。混合样本中的单人空棋盘来自 1220 队列，没有将其误判成排位损坏。

**验证与限制**：9 项新增测试通过，覆盖凭据不泄漏、固定域名、错误停止、占位版本、去重、精确 ID 及同一玩家同一持有者的联合条件。原 OP.GG 阵容仍 ready，678 条知识向量保持可用。当前统计尚未改用 Riot；需继续核定补丁、处理缺少的实体映射及扩大有效样本。王者榜的采集时段位不代表同局每个对手在比赛时的段位，也不能把最终阵容当作逐回合棋盘。

**经验**：依次区分“认证成功、取得记录、字段合格、版本归属、样本足够、可公开查询”，每层都要有实际证据。官方来源也需要质量检查；过滤队列后再计算完整性和覆盖率，避免把不同玩法混成一个结论。

## 13. Riot 同时限制每秒与两分钟请求数

**现象与证据（2026-10-10）**：用户确认当前 Key 配额为 20 次/秒、100 次/120 秒。这是同时生效的两个窗口，不能按 20 次/秒持续采集；长期理论上限约为每分钟 50 次请求，还包含榜单、比赛列表等开销。此前 16 次真实验收请求全部成功，没有观察到 429，不能将此记录描述成已经发生的限流故障。[官方限流说明](https://developer.riotgames.com/docs/portal#rate-limiting)另列出了应用、方法、服务三个层面的限制。

**现有边界与改法**：原探针每次串行间隔至少 1350 ms，单次最多 16 请求，本身已低于用户提供的两个限额。此次增加单进程共用的双滑动窗口计数，保留 1350 ms 最小间隔；即使同一进程内有多个调用者，也先排队预约配额再发请求。KR 与 ASIA 在本地保守共用这份预算。429 仍立即结束本轮探针，同时将 `Retry-After` 应用于本进程的后续请求；缺失时默认冷却 120 秒。401/403 仍停止，不自动重试或更换凭证。

**实际验证**：`node --test tests/riot-probe.test.mjs tests/riot-rate-limiter.test.mjs tests/riot-sample-audit.test.mjs` 共 14 项通过。虚拟时钟模拟 201 个并发预约，验证两个窗口均不超额；另验证默认间隔、冷却不被缩短、无 Retry-After、等待失败后的队列恢复，以及请求发送前预约和 429 冷却传递。本次没有再次请求 Riot，也没有调用付费模型。

**残留与经验**：计数只保存在当前进程，重启、多个命令进程或外部程序共用 Key 的配额未统一管理；未接入动态响应头中的方法与服务限额，所以仍需正确处理 429。当前网页与 Agent 没有调用 Riot，探针不承担正式采集。正式后台采集需使用 Redis 统一调度和冷却、比赛 ID 去重及断点续采，再由查询接口读取本地数据库。请求配额不是有效排位场数，更不是某个英雄与装备联合条件的样本数。

## 14. 从能调用 API 到能回答同阵容装备统计

**现象与根因（2026-10-10）**：原筛选器只有 OP.GG 聚合快照，数据库没有比赛、玩家终局和装备关联，三个英雄的边际统计不能拼成同阵容样本。Riot Key 通过与少量 JSON 落盘也不等于网页已经能查。独立探针的限流状态不会跨进程共享，不能直接充当每日采集器。

**改法**：新增六张 Riot 表及迁移 003/004；比赛去重、模式与完整性校验、版本归属和派生行入库在事务中完成。MySQL 保存待采 ID 和分页游标，Redis 用服务器时间与原子 Lua 统一配额、请求间隔和 429 冷却；Redis 不可用时停止上游请求。独立 worker 每 24 小时最多补采 25 场，进度与下一次运行时间持久化。筛选器与 Agent 共用参数化 SQL，先限定同一玩家终局，再聚合三栏；全程只读一致性事务，防止采集中三栏分母发生变化。

**这轮具体踩到和发现的问题**：

- `game_datetime` 不是这批比赛的开始时间。实测第一场 `gameCreation` 与它相差 2118.228 秒，`game_length` 为 2115.217 秒。归档改用开始和结束时间均落在同一推定窗口；日期窗口不等于已核验的地区换版瞬间。
- 官方韩文公告有 10 月 8 日热修，PC/移动端不同步。主补丁推定保留独立标记，热修未知；没有将 API 占位版本改写成 18.4B。
- 未知药水不应让已经识别的整场棋子都消失。原始 ID 留存并进入映射缺口，只排除受影响棋子的完整三件套；玩法或结构不合格仍整场隔离。
- 同一英雄可能存在多个实例。装备必须在同一实例上满足条件，且相同英雄、相同三件套的多个实例对该分组只计一份玩家终局；总场数与玩家终局数分别展示。
- 单看原始指纹不能判断派生数据是否仍有效。增加派生指纹，图鉴的槽位、唯一性或类别变化会触发重新分类；版本证据恢复后也重新处理数据库中隔离原始记录，不会因为“比赛已存在”永远跳过。
- 沿用第 9 条经验，增加原始 JSON 文本列，防止未来 MySQL 二进制 JSON 的浮点重序列化影响摘要。此次实际核对最初 62 份记录的摘要差异为 0；这是预防措施，没有虚构这批数据已经发生摘要损坏。无可核验文本的旧记录若摘要不符则保留待核验，不当作新的上游冲突。
- 原 UI 队友行依赖来源阵容 ID，Riot 分组没有这种 ID。改为真实统计显示，避免跳转到不存在的 OP.GG 阵容详情；新增出装目标选择且保留装备自己的佩戴者条件。
- 原 Agent 单英雄预取断言与新共用查询工具不一致，更新为验证完整条件、持有者及无结果不放宽。空筛选器上下文也不能覆盖用户明确的多英雄问题。

**实际验证**：全套自动化 330/330 通过，无跳过。第一次沙盒运行无法连接本机测试服务器，改为允许本机 HTTP 后才完成全套；另修复两项旧工具路径断言，未将它们归因于上游。真实 Redis 四项检查通过（共享间隔 1353ms、2 秒冷却实际 2004ms、两个配额窗口）；真实 MySQL 九项边界检查通过，测试行在未提交事务内生成并回滚，残留为 0。原始棋盘与三英雄＋绑定装备查询逐条比对一致，Agent 检索预览成功但未调用付费聊天模型。浏览器实际验证三栏、出装目标切换、小样本提示和开发者面板，没有浏览器错误。

**数据结果**：原 12 场、手动补采 50 场、worker 首轮 25 场合计 87 场；36 场符合当前范围，288 份玩家终局可查，51 场因玩法、结构或窗口隔离。50 场采集共 58 请求，worker 25 场共 27 请求，均完成；已有比赛分别跳过 13 与 8 次，不能把这些次数算作新增比赛。重放 87 场后第二遍全部为 duplicate，样本数保持不变，87 份原始 JSON 文本已保存。首页仍返回 10 套原阵容，Milvus 678 个片段保持可用。验收详情见 [RIOT_PIPELINE_VALIDATION.json](RIOT_PIPELINE_VALIDATION.json)，运行方式见 [RIOT_PIPELINE.md](RIOT_PIPELINE.md)。

**残留与经验**：这些是少量种子玩家的终局样本，不能声称全服代表性、当局段位、逐回合过程或可靠的稀有条件排名。当前补丁仍为按保守比赛时间窗口推定，地区精确生效时刻和热修未知。开发 Key 24 小时失效后需要用户更新并重建 worker；自动采集不等于自动续签 Key。每日任务仅针对 Riot，OP.GG、知识来源和完整赛季发布仍需各自维护。新安装没有 Riot 原始种子，默认先使用原已发布资料，填写自己的 Key 后才开始积累比赛。

## 16. 术语问题要分清模型知识、实体识别与检索证据

**现象与审计（2026-10-10）**：用户怀疑 Agent 不懂云顶术语，询问是否需要上传术语文档。按用户要求显式调用配置的 `deepseek-flash`：一次 24 题无检索测试、两句真实 Agent 问答（合计 6 次聊天补全）、一次带本地词典的对照，共 8 次聊天 API 请求。提供方记录合计 41,718 输入 / 2,157 输出 / 43,875 总 token；未查询余额，未推测费用。不能通过输出检查预训练语料，这只是当前 API 在这些具体输入下的行为。

**直接证据**：

- 无检索时，前 11 个实体外号中 10 个核心名称映射正确；“板甲”被答成“荆棘背心”，而项目核对的映射是石像鬼石板甲。这个小样本只检查核心名称，不是全部回答的准确率：模型还擅加了历史费用、效果和昵称来历，未逐条认可。
- 慢D、大D、抢节奏等基本概念有一定理解；对“妮蔻”“法杖”的歧义能说明需上下文，未凭记忆编造当前联合胜率。针对测试中自造的“星砂回响连锁”表示不确定。
- 实际 Agent 问“豹女和木木同时上场，豹女带饮血，查最佳三件套及样本量”：先搜“豹女 木木”未成功，又查正式名称。4 次工具配额被名称查询和单英雄出装查询用完，后续联合查询未执行，回答虽说明口径不同，仍提供了用户没要求的单英雄统计。这是实际失败用例，不能称为联合查询通过。
- 运营术语问答触发 `search_knowledge`，这次线上实际返回 `retrieval.mode=lexical`，命中花仙子金币、奖励和连败类强化出现条件，缺少术语定义。模型给出的额外等级概率与运营延伸不应因为附有引用就视为已核验答案。

## 24. Agent 自然语言查询必须执行本轮工具，并与页面共享统计口径

**具体改法**：增加 `server/query-agent.mjs`，让模型将自然语言转换为经过目录 ID、视图字段、持有者、数量、门槛和排序校验的工具参数。推荐阵容、棋子整体、装备整体、羁绊档位、三件套、装备携带者及组合筛选调用各页面同一后端服务，继续由 MetaTFT/MySQL 返回统计。参数不支持时明确失败，不静默删除条件。首页体系与筛选器同场组合、整体与出装、持有者与队友、羁绊各激活档位分别处理。筛选接口补出已保存的总体指标，不从各行相加推导总体。证据标题改为实际来源。前端保存最近一次已执行的规范查询，支持连续追问；新问题优先于旧页面条件。筛选查询可点击“在筛选器查看”，复用页面校验与 URL 状态，保持装备绑定、重复数量、门槛和排序。
